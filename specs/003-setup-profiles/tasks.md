# Tasks: Setup Profiles

**Input**: Design documents from `specs/003-setup-profiles/`

**Prerequisites**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/](contracts/), [quickstart.md](quickstart.md)

**Tests**: Included. The constitution (Principles II and III) and research R17 require test-first work for every rule-bearing unit, contract tests for every new HTTP contract, Supertest and role matrix rows for every new portal route, and a shared case file for the two answer file validators. Within each phase, test tasks come first and must fail against the current code before the implementation tasks start. New tests exercise real code (services, repositories and functions over the in-memory test doubles); they never assert a literal against itself, which is how several existing files under tests/CloudImaging.ImagingCoreApi.Tests/Integration/ are written today.

**Organization**: Tasks are grouped by user story so each story can be implemented and verified on its own.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependency on an incomplete task)
- **[Story]**: User story the task belongs to (US1 to US5)
- Every task names the exact file(s) it changes

## Writing rules for every task

- Files touched by a task contain no em dash, en dash, middle dot, right arrow or smart quotes (U+2014, U+2013, U+00B7, U+2192, U+201C, U+201D, U+2018, U+2019) when the task is done. ASCII punctuation only; navigation paths use "A > B".
- No spec, requirement, success criterion, task or story identifier (for example a requirement number, a task number, a story label or "spec 005"), and no pointer to one, appears in UI text, tooltips, dialogs, toasts, error and validation messages, exception text, log messages, API responses, the device log written by the setup runner, script output, Bicep descriptions, docs or release notes. Code comments are the only place they are allowed.
- User-facing strings are taken verbatim from the contracts (contracts/portal-client-surfaces.md, contracts/portal-server-routes.md, contracts/answer-file-rules.md, contracts/setup-runner-and-unattend.md section 6, contracts/device-gateway.md).
- PowerShell follows `.github/copilot-instructions.md` "General PowerShell Practices". Portal frontend follows `.github/instructions/portal-ui.instructions.md` (primitives from `components/ui/`, every button is `Button` with the variant chosen by purpose and no size prop except `size="icon"`, 12/16/20/24 icons, 4px grid, weights 400/500/600, `aria-label` on icon-only controls, absolute timestamps through `formatDateTime`, one-line table rows).
- New enums in `CloudImaging.Contracts` carry `[JsonConverter(typeof(JsonStringEnumConverter))]` like every existing enum, so values travel as strings.
- Test names follow `MethodOrScenario_StateUnderTest_ExpectedBehavior` (.NET) and plain sentences (Vitest).

1. Setup and Foundational: contracts and the optional-step rule in place; no behaviour change for existing deployments.
2. US1: registry values end to end (backend and Client streams).

5. US4: history, restore and retention.
6. US5: Start imaging overlay lines.
7. Polish: docs, release notes, scans, full checks and coverage, then tenant, device and performance verification. The maintainer then runs the releases manually in the order backend, Media Builder, Client, with the notes files on `main`.

### Parallel Team Strategy

- Developer A: Core and Operator API (US1 Core, then US3 validator, then US4).
- Developer B: Client and setup runner (US1 Client, then US2), plus Media Builder.
- Developer C: Portal backend and frontend (US1 portal, then US2 and US3 dialogs, US4 history, US5 overlay), then docs.
