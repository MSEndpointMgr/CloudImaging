**Input**: User description: "Build a solution that applies a Windows operating system image from the cloud involving a Client WPF application running in WinPE..."

## Clarifications *(notes from specification refinement)*

### Session YYYY-MM-DD (June 15, 2026)

- **Q: SAS Token Refresh Trigger (FR-008)** → **A: Cloud Imaging Client MUST poll the Device Gateway API every 30 seconds for state updates, which include a SAS token for Storage Account access. When the SAS token expiry time is less than 15 minutes away, the client MUST request a fresh token from the Device Gateway API before continuing the download. This provides a 15-minute safety buffer for token refresh and network resilience.**
- **Q: Session State Lifecycle** → **A: (SUPERSEDED by Q5, June 17, 2026 -- SessionPendingApproval removed; SessionNotAuthorized is now the terminal state for non-matching devices when pre-flight authorization is enabled; see 4-view architecture clarification below) SessionInit: Client starts, registers session, and submits device serial number and manufacturer/model to the Device Gateway API. SessionPendingApproval (conditional): When device pre-flight authorization is enabled and the device serial number is not found in either Autopilot V1 registered devices or Intune Corporate Identifiers, the session waits for explicit operator approval in the Portal before proceeding; this state is skipped entirely when pre-flight authorization is disabled or when the device is matched. SessionAllowed: Pre-flight checks passed (or pre-flight is disabled), session is ready to be coupled by an operator. SessionAssigned: Session is coupled from Cloud Imaging Portal and client is authorized to request SAS token and Storage Account download details. SessionStarted: Automatically transitions from SessionAssigned on the next 30-second polling interval when the client detects Assigned and requests details; no additional local technician action is required on the device. SessionInProgress: Client relays per-step imaging status (format-disk, retrieve-metadata, download-image, apply-image) to the Imaging Core API for real-time portal visibility. SessionCompleted/SessionFailed: Terminal outcomes for successful completion or unrecoverable failure.**
- **Q: Device Session Passcode Format** → **A: 6-character alphanumeric passcode format: uppercase letters (A-Z) and digits (0-9) only, with ambiguous characters excluded (I, O, 1, 0). This ensures high readability on WinPE screens, minimizes typos during manual portal entry, and provides ~1 billion unique codes (32^6 ≈ 1B). Passcode MUST be case-insensitive for portal input validation.**
- **Q: Passcode Security Model** → **A: The session passcode is a short-lived, one-time pairing code generated server-side (Imaging Core API via Device Gateway API), returned to the client only for local display, and never re-used as an ongoing API credential. Ongoing client polling and progress/report operations use a separate high-entropy device-session token issued at SessionInit. The passcode is invalidated immediately after successful coupling or expiry and is stored only as a hash at rest.**
- **Q: Device-Session Token Properties** → **A: The device-session token is a server-generated, opaque bearer credential issued at SessionInit by the Device Gateway API on behalf of the Imaging Core API. It is distinct from both the one-time pairing passcode and any Entra ID access token, is never shown to technicians, is bound to the specific device session, and is used only for ongoing client polling, progress reporting, and SAS refresh requests until the session ends or the token expires.**
- **Q: Overall Imaging Completion Percentage Calculation (FR-007, FR-024)** → **A: Overall imaging completion percentage is computed using uniform step-milestone weighting: (completed steps / total steps for the session) x 100, truncated to integer (0-100). The set of steps is fixed at the point the session transitions to SessionStarted and includes all defined imaging steps (format-disk, retrieve-metadata, download-image, apply-image, and any additional session-specific steps). The hyphenated forms (format-disk, retrieve-metadata, download-image, apply-image) are the machine-readable step identifiers used in API payloads and DTO values; the natural-language forms in FR-007 are for human readability only. The download step is a single step unit; it may expose sub-progress via the optional stepProgressPercent field on its ImagingStep record but contributes fractional value to overallProgressPercent only upon completion of that step. This rule ensures a deterministic, reproducible percentage across all implementations and API layers.**

### Session June 16, 2026

- **Q: Observability Strategy** → **A: All Azure Function Apps (Device Gateway API, Operator API, Imaging Core API) and the Cloud Imaging Portal backend MUST emit structured telemetry to a single shared Azure Application Insights workspace (requests, dependencies, exceptions, custom traces). WPF applications (Cloud Imaging Client and Cloud Imaging Media Builder) MUST write structured diagnostic logs to a local rolling log file only and MUST NOT require network connectivity to an external APM service during operation. The shared App Insights workspace is provisioned by the Bicep deployment package; its connection string is injected via deployment parameters with no hardcoded instrumentation keys.**
- **Q: API Versioning Scope** → **A: Public versioned API routing is required for Device Gateway API only. All device-facing endpoints MUST be exposed under a URL path version prefix (`/api/v1/`). Operator API and Imaging Core API are deployment-coupled internal/operator surfaces for v1 and do not require explicit URL version prefixes in this release.**
- **Q: Service Availability Target** → **A: Device Gateway API, Operator API, and Imaging Core API together MUST maintain a v1 service availability target of 99.5% monthly uptime, measured across all three components. Planned maintenance windows (communicated >= 7 days in advance) are excluded from this calculation. Self-hosters are responsible for achieving this target within their own Azure deployments; the CloudImaging solution design and deployment templates support this goal.**
- **Q: Rate Limiting Scope** → **A: Per-session rate limiting is applied to the Device Gateway API only, authenticated by device-session token. Each device session is limited to a maximum of 10 API calls per 30-second window. Requests exceeding this limit return HTTP 429 (Too Many Requests). Operator API and Imaging Core API do not implement rate limiting in v1, as they are called by controlled server components within a known deployment topology.**

### Session June 17, 2026 (continued)

- **Q: Cloud Imaging Client Workflow Sequence** → **A: (SUPERSEDED by Q3, June 17, 2026 -- retrieve-metadata is now a session init concern, not a visible imaging step; 3 visible steps are format-disk, download-image, apply-image; see imaging steps and 4-view architecture clarifications below) The Cloud Imaging Client executes the following step sequence on a target device during an imaging session: (1) format-disk: Partition and format the target system disk, (2) retrieve-metadata: Query device hardware metadata (motherboard, BIOS version, NIC identifiers, storage layout) for audit/logging, (3) download-image: Download the OS image from Blob Storage via SAS URL (checking cache first), and (4) apply-image: Apply the downloaded OS image to the target disk using Windows imaging tools (DISM or equivalent). Each step reports status and optional sub-progress back to the Device Gateway API in real-time. The step set is fixed when SessionStarted is issued by the Imaging Core API. Additional steps are deferred to v2.**
- **Q: Device Pre-Flight Authorization Model** → **A: (SUPERSEDED by Q5, June 17, 2026 -- no-match now immediately produces SessionNotAuthorized terminal state; no operator approval flow exists in v1; see 4-view architecture clarification below) The Imaging Core API performs a single unified device authorization pre-flight check at the SessionInit -> SessionAllowed transition. The Cloud Imaging Client submits the device serial number (Win32_BIOS.SerialNumber) and manufacturer/model (Win32_ComputerSystem.Manufacturer, Win32_ComputerSystem.Model) as part of session registration. The Imaging Core API queries Microsoft Graph in parallel against two sources: (1) Autopilot V1: GET /deviceManagement/windowsAutopilotDeviceIdentities?$filter=serialNumber eq '{serial}' (v1.0) for devices pre-loaded with a hardware hash, and (2) Intune Corporate Identifiers: GET /deviceManagement/importedDeviceIdentities?$filter=importedDeviceIdentifier eq '{manufacturer},{model},{serial}' (beta) for devices pre-loaded for Autopilot Device Preparation (V2). If either check returns a match the session transitions to SessionAllowed automatically. If neither matches, the session is held at SessionPendingApproval and an operator must explicitly approve the device in the Cloud Imaging Portal before imaging can proceed. Pre-flight authorization is a Portal-configurable setting (enabled or disabled) accessible to administrators; when disabled, all sessions automatically advance from SessionInit to SessionAllowed without performing any Graph lookups. The Imaging Core API requires the DeviceManagementServiceConfig.Read.All application permission on its managed identity to perform the Graph queries.**
- **Q: Cloud Imaging Client branding delivery model** → **A: (SUPERSEDED by Q6, June 17, 2026 -- branding logo is now embedded within the boot image WIM during the Generate Boot Image workflow, not separately written to the bootable partition during USB preparation; Entra ID sign-in at app launch is required for branding retrieval during Generate Boot Image; see Media Builder sign-in scope and branding delivery in boot image clarification above) The branding logo displayed in the Cloud Imaging Client WinPE UI is embedded into the bootable partition by the Cloud Imaging Media Builder during USB storage device preparation. The Media Builder retrieves the configured branding logo from the Storage Account via a SAS URL obtained from the Operator API at USB preparation time and writes the logo asset to the bootable partition. If no custom branding logo is configured in the Portal at the time of USB preparation, the Media Builder MUST embed the MSEndpointMgr default logo as a fallback. Portal branding MUST therefore be configured before USB storage devices are prepared for custom branding to appear on the Cloud Imaging Client UI. Re-preparation of USB media is required to update the embedded branding. The Cloud Imaging Client reads the logo from the bootable partition filesystem at startup; no network fetch of branding occurs at client runtime.**
- **Q: Cloud Imaging Client startup operation selection screen** → **A: On launch, the Cloud Imaging Client MUST display an operation selection screen showing the application title "Cloud Imaging" and two operation cards: "Imaging" (active) and "Decommissioning" (visually disabled, labeled as a future capability). The app auto-launches when WinPE boots but does NOT automatically start a session or make any API call. The technician MUST explicitly select the Imaging card and confirm with a Continue action before session registration begins. Decommissioning is out of scope for v1 and MUST NOT be accessible.**
- **Q: Cloud Imaging Client imaging steps, UI step labels, and terminal result screen** → **A: retrieve-metadata is NOT a visible imaging step and does NOT appear in the step progress bar UI. Hardware metadata collection (motherboard, BIOS version, NIC identifiers, storage layout) is executed silently at session initialization and submitted to the backend as part of the session registration payload for audit/logging purposes. The three visible imaging steps tracked in the step progress bar are: (1) format-disk, displayed as "Format"; (2) download-image, displayed as "Download"; (3) apply-image, displayed as "Apply". overallProgressPercent is calculated on these 3 steps only: (completed steps / 3) x 100, truncated to integer. This supersedes the 4-step sequence stated in the Cloud Imaging Client Workflow Sequence clarification above (retrieve-metadata is now session init context, not a progress step). After the Apply step completes, the Cloud Imaging Client MUST display a terminal result screen: a success/completion view when the session reaches SessionCompleted, or a failure view showing a support reference code and remediation guidance when the session reaches SessionFailed.**
- **Q: Cloud Imaging Client WinPE resolution and window layout** → **A: The Cloud Imaging Client WPF window MUST target a minimum display resolution of 800x600 pixels. The window MUST be centered both vertically and horizontally on the display at all times. All UI elements across all screens MUST fit within the visible window area at 800x600 without requiring vertical or horizontal scrolling. Fixed-layout design is required to maintain this constraint across all supported screens (operation selection, session waiting/passcode, imaging progress, terminal result).**
- **Q: Cloud Imaging Client 4-view architecture and authorization model** → **A: The Cloud Imaging Client implements exactly four views in sequential order: (1) OperationSelectionView - operation cards shown, no session initialized, no API calls made; (2) SessionInitView - session is initialized on view activation and device authorization check runs immediately; if authorized, the session appears in the Portal for coupling and the view shows the session ID and passcode while awaiting operator assignment; if authorization fails, the client transitions immediately to ResultsView with a Not Authorized result; (3) ProgressView - shows the three imaging steps (Format, Download, Apply) with current progress and step-level detail; (4) ResultsView - shows the terminal outcome: Success, Failure (with support reference code and remediation), or Not Authorized (with device serial number and enrollment guidance). SessionPendingApproval is superseded and removed: failed authorization results in SessionNotAuthorized (terminal state) and immediate transition to ResultsView. No manual operator approval flow exists in v1; the Portal pre-flight authorization toggle (FR-026a) controls whether the check runs globally, not whether individual devices can be manually approved.**
- **Q: Cloud Imaging Media Builder sign-in scope and branding delivery in boot image** → **A: Entra ID sign-in MUST be required at application launch as the first user interaction; SignInView MUST be the first screen before OperationSelectionView or any workflow. Both the Generate Boot Image and Prepare USB Storage Device workflows require Entra ID authentication to access the Operator API: Generate Boot Image retrieves the configured branding logo from the Operator API and embeds it alongside the Cloud Imaging Client executable within the boot image WIM artifact so the Client loads branding from its own executable directory at startup; Prepare USB Storage Device retrieves the boot image via SAS URL. The branding logo is already embedded in the boot image WIM; no separate branding retrieval step is required during USB preparation. If no branding logo is configured in the Portal at Generate Boot Image time, the MSEndpointMgr default logo MUST be embedded as a fallback. Updates: FR-052 (sign-in at app launch, not only at Prepare USB entry), FR-051 (boot image WIM includes branding logo alongside Client executable), FR-053 (no separate branding retrieval during USB prep), FR-002a (Client reads branding from its own executable directory).**
- **Q: Cloud Imaging Media Builder Windows ADK prerequisite check scope** → **A: The OperationSelectionView MUST verify that Windows Assessment and Deployment Kit (ADK) and the Windows PE add-on for the ADK are installed on the technician workstation before enabling any workflow. Detection targets: copype.cmd and makewinpemedia (both part of the ADK WinPE add-on). If either component is not detected, BOTH the Generate Boot Image and Prepare USB Storage Device workflow cards MUST be visually disabled and a clear installation requirement message displayed; the technician MUST NOT be able to proceed with either workflow until the required components are installed. Updates: FR-050 (4-view architecture for Media Builder), FR-050a (new: ADK prerequisite check).**- **Q: Cloud Imaging Media Builder GenerateBootImageView source options for Cloud Imaging Client binaries** → **A: The GenerateBootImageView MUST offer two mutually exclusive source options for the Cloud Imaging Client binaries: (1) Automatic download -- the app calls the MSEndpointMgr GitHub public releases API to resolve the latest release tag and downloads the Client binaries directly with a real-time progress indicator; internet access is required for this option; (2) Custom local path -- the technician specifies a local filesystem path to pre-downloaded Client binaries, supporting offline and airgap deployments. The GenerateBootImageView MUST also allow the technician to specify an output folder path for the generated boot image WIM artifact before generation begins. Updates: FR-051a (new: GenerateBootImageView source options and output folder).**
- **Q: Cloud Imaging Media Builder GenerateBootImageView post-generation upload behavior** → **A: Upon successful generation, the GenerateBootImageView MUST display a completion notification showing the full output folder path of the generated boot image WIM and provide clear next-step instructions directing the technician to upload the WIM file manually via the Cloud Imaging Portal boot image catalog. The Cloud Imaging Media Builder app MUST NOT perform the portal upload itself; upload is a manual step performed by the technician through the Cloud Imaging Portal web UI. Updates: FR-051b (new: completion notification with output path and next-step upload instructions).**
- **Q: Cloud Imaging Media Builder PrepareStorageDeviceView USB device detection criteria and Cloud Imaging Client cache skip behavior** → **A: The PrepareStorageDeviceView MUST list devices matching both (1) bus type = USB and (2) removable flag = true; no minimum capacity threshold is applied. Disqualified devices (wrong bus type or not removable) MUST be excluded from the selectable list entirely; the host OS/system disk MUST always be blocked. Additionally, the Cloud Imaging Client cache behavior on space pressure is updated: if insufficient space is available on the USB cache partition to store a new OS image (after 30-day auto-purge cleanup), the Client MUST skip cache storage for that session and proceed with a direct download without error; no LRU eviction of existing valid cache entries is performed. Updates: FR-054 (USB bus type + removable flag detection criteria), FR-009d (cache skip on insufficient space; no LRU eviction on space pressure).**

### Session June 22, 2026

- **Q: Portal authorization model, user roles, and Entra ID app registration strategy** → **A: The solution uses two user-level app roles defined on a single shared Entra ID enterprise app registration: `CloudImaging.Administrator` (full access to all Portal features and both Media Builder workflows) and `CloudImaging.Technician` (Portal access limited to viewing all device sessions, coupling sessions by passcode, assigning OS images from the existing active catalog, initiating bulk assignment, monitoring imaging progress, and viewing the OS image catalog in read-only mode; OS image management, boot image lifecycle, branding configuration, and deployment configuration are restricted to Administrators). Both the Cloud Imaging Portal and the Cloud Imaging Media Builder authenticate users against this same shared enterprise app registration; user role assignment is managed in Entra ID. In the Media Builder, users with the `CloudImaging.Technician` role see only the Prepare USB Storage Device workflow; the Generate Boot Image card is hidden or disabled for Technician-role sign-ins. Portal backend enforces role restrictions before forwarding requests to the Operator API. The Operator API service-level roles (`CloudImaging.PortalAccess` for the Portal backend service principal; `CloudImaging.MediaBuilderAccess` for the Media Builder service principal) remain as the Operator API access enforcement layer; user-level role enforcement is applied at the Portal backend and Media Builder application layers. Updates: FR-040 (role enforcement reference), FR-040a (new: Portal user role access matrix), FR-040b (new: shared enterprise app registration), FR-050 (OperationSelectionView role-based card visibility reference), FR-050b (new: Media Builder role-based feature visibility), FR-052 (shared enterprise app reference), FR-061 (service-level and user-level role model clarified).**
- **Q: Cloud Imaging Client ResultsView retry behavior on failure** → **A: On the Failure outcome in ResultsView, the Retry action MUST navigate the app back to OperationSelectionView (view 1 of 4) without requiring a hardware reboot. The technician re-selects the Imaging operation, which bootstraps a fresh session with a new passcode. The previous SessionFailed session is not resumed. The portal operator couples the new session using the new passcode. Because the new imaging sequence starts with format-disk, the target disk is cleanly reinitialised regardless of how far the previous attempt progressed. Update: FR-007b (Retry navigates to OperationSelectionView).**
- **Q: SC-001 "standard-tier deployment" reference baseline** → **A: A standard-tier deployment is defined as approximately 50 Mbps WAN link, approximately 10 GB OS image (WIM/ESD), and Azure Functions Premium (EP1) plan. This baseline provides pre-warmed Function instances (no cold-start penalty) and a predictable latency floor suitable for validating the 15-minute completion window at up to 1000 sessions/day. Update: SC-001 (baseline definition appended).**
- **Q: Boot image catalog maximum active entries** → **A: The boot image catalog supports a maximum of 5 active entries. All active entries are eligible for selection in USB preparation sessions; the latest published entry is pre-selected as the recommended default but the technician may choose a different active entry (for example, a previously known-good boot image for a specific hardware model). Older entries may be retained and remain selectable until they are explicitly deleted. Update: SC-008 (boot image catalog scale appended), FR-063 (scale constraint note added).**
- **Q: GitHub releases API failure behavior in FR-051a (Automatic download option)** → **A: If the GitHub releases API or binary download fails, the app MUST retry up to 3 times with exponential backoff. If all 3 attempts fail, the app MUST display a clear error message indicating the download could not be completed; no automatic fallback or prompt to switch source option is shown. The technician may then manually select the Custom local path option. Update: FR-051a (retry and error behavior appended).**
- **Q: Support reference code format** → **A: Support reference codes MUST use the structured format {ComponentCode}-{SessionRef}-{StageCode}-{EpochSeconds}, where: ComponentCode is a 3-letter prefix (CIC = Cloud Imaging Client; CMB = Cloud Imaging Media Builder); SessionRef is the first 8 characters of the associated session ID for Cloud Imaging Client operations, or a short operation-stage identifier for standalone Media Builder operations without a session context; StageCode is an abbreviated step identifier (REG=session-registration, FMT=format-disk, DWN=download-image, APL=apply-image for the Client; DVI=disk-validation, PRT=partitioning, BID=boot-image-download, BCF=boot-config for the Media Builder); EpochSeconds is the Unix epoch at time of error (seconds since 1970-01-01 UTC). Example: CIC-A1B2C3D4-DWN-1750000000. Updates: FR-006, FR-009, FR-058 (support reference code format defined).**
- **Q: ResultsView Not Authorized outcome action buttons** → **A: The Not Authorized outcome in ResultsView MUST display only a single Exit/Close action. No Retry button is shown because imaging cannot proceed until the device is enrolled in Autopilot or added as an Intune Corporate Identifier; re-imaging requires the operator to enroll the device and the technician to reboot and start a new session. Update: FR-007b (Not Authorized outcome - Exit/Close action only; no Retry button).**
- **Q: SessionInitView back-navigation** → **A: No back-navigation from SessionInitView is available. Once the technician confirms the Imaging operation and session registration begins, the Cloud Imaging Client MUST NOT provide a back or cancel action on SessionInitView. To abort, the technician must reboot the device; the registered session expires naturally by inactivity. Update: FR-001a (no back-navigation from SessionInitView).**
- **Q: Session passcode standalone TTL** → **A: The passcode has its own TTL that is a distinct configurable deployment parameter (default: 30 minutes), independent of the session inactivity timeout. Once the passcode TTL elapses without successful coupling, the passcode is invalidated; the session MAY remain in SessionAllowed if the session inactivity timeout has not yet elapsed, but no new passcode is issued without a device reboot. Updates: FR-021 (passcode TTL as distinct configurable parameter), FR-042 (passcode TTL as externalized deployment parameter).**
- **Q: OS image upload mechanism** → **A: OS image upload from the Cloud Imaging Portal MUST use a staged direct-to-blob upload flow: the Portal backend requests an upload SAS token URL from the Operator API (which brokers the request to the Imaging Core API), and the browser uploads the image file directly to the Storage Account blob using that URL. The image MUST NOT be added to the active catalog until the upload is fully committed and the SHA256 hash is verified. This is consistent with the boot image upload pattern (FR-051). Update: FR-036 (staged direct-to-blob upload mechanism specified).**
- **Q: PrepareStorageDeviceView USB device list refresh behavior** → **A: The device list MUST auto-refresh in response to device plug and unplug events using Windows DeviceWatcher (or equivalent WMI DeviceChanged notification); newly connected qualifying removable USB devices MUST appear automatically and disconnected devices MUST be removed. A manual Refresh button MUST also be present as a fallback. Update: FR-054 (auto-refresh on plug/unplug + manual Refresh button).**
- **Q: USB bootable partition minimum size** → **A: The bootable WinPE partition MUST have a minimum size of 2 GB, providing comfortable headroom above the typical WinPE + Cloud Imaging Client payload (under 1 GB) and accommodating near-term growth. The cache partition minimum is 24 GB, sized to hold one OS image at the 20 GB supported maximum plus filesystem overhead. Updates: FR-055 (2 GB minimum boot partition, 24 GB minimum cache partition), Assumptions (boot partition minimum size clarified).**
- **Q: Maximum supported OS image size** → **A: The platform MUST support OS images (WIM/ESD, or the install image extracted from an uploaded ISO) of up to 20 GB. This is a capability ceiling, not the SC-001 performance baseline, which remains defined at approximately 10 GB. Uploads are staged in 8 MB blocks (about 2 560 blocks at the maximum, well inside the Blob Storage 50 000 block limit) under a 24 hour SAS, and verification and ISO extraction run asynchronously rather than inside any HTTP request. Updates: FR-036 (20 GB ceiling), FR-055 (cache partition minimum raised to 24 GB accordingly).**
- **Q: Media Builder SignInView authentication failure handling** → **A: If Entra ID authentication fails for any reason (incorrect credentials, MFA failure, network timeout, or token error), the Media Builder MUST display an inline error message on SignInView describing the failure and provide a Retry sign-in button. The app MUST NOT navigate away from SignInView on auth failure; SignInView remains the active screen until sign-in succeeds or the user closes the application. Update: FR-052 (auth failure inline error and Retry button on SignInView).**
- **Q: SAS token URL expiry configuration location and scope** → **A: The OS image SAS token URL expiry window is a portal configuration setting stored in the PortalConfiguration record as sasTokenUrlExpiryMinutes (default: 240 minutes / 4 hours). Only users with the CloudImaging.Administrator role can modify this setting via the Portal deployment configuration section. Changes take effect immediately for all newly issued SAS token URLs; sessions with already-issued SAS token URLs are not retroactively affected. Updates: FR-022 (SAS expiry references PortalConfiguration), PortalConfiguration entity (sasTokenUrlExpiryMinutes field added).**
- **Q: Passcode uniqueness scope and reuse across sessions** → **A: The 6-character passcode uniqueness constraint is scoped to currently active (non-terminal, non-expired) sessions only. Passcodes from sessions that have reached a terminal state (SessionCompleted, SessionFailed, SessionNotAuthorized) or expired are considered released and MAY be reused for new sessions. The session ID is the true unique session identifier; the passcode is a short-lived human-readable coupling key valid only within the context of an active session. The Imaging Core API MUST generate a passcode unique among all currently active sessions; on collision it MUST retry up to 3 times; if all 3 attempts collide, session registration MUST fail with HTTP 500. Updates: FR-010, FR-021 (passcode uniqueness scoped to active sessions; reuse after terminal/expiry permitted; collision retry logic defined).**
- **Q: Cloud Imaging Portal navigation structure and Sessions section layout** → **A: The Cloud Imaging Portal MUST use a fixed left sidebar navigation with five labeled sections in order: Sessions (default landing page after authentication), OS Images, Boot Images, Branding, and Configuration. Navigating between sections replaces the main content area without a full page reload. The Sessions section MUST present a session table with per-row checkboxes, Select All and Deselect All controls, a [Couple Device] toolbar button, and filter tabs above the table. Updates: FR-031 (session dashboard layout), FR-040 (sidebar navigation structure).**
- **Q: Cloud Imaging Portal Sessions section filter tabs and default view** → **A: The Sessions section MUST display four filter tabs above the session table: Active (default), Completed, Failed, and All. The Active tab shows sessions in Allowed, Assigned, SessionStarted, and SessionInProgress states. The Completed tab shows SessionCompleted sessions only. The Failed tab shows SessionFailed and SessionNotAuthorized sessions. The All tab shows every session regardless of state. Each tab MUST display a real-time count badge reflecting the current number of sessions in that state group. The Active tab MUST be selected by default on page load so that terminal sessions do not clutter the primary operator workflow view. Updates: FR-031 (session dashboard filter tabs, Active default, real-time count badges).**
- **Q: Cloud Imaging Portal session coupling passcode entry modal** → **A: The Sessions section MUST provide a persistent [Couple Device] toolbar button that opens a modal dialog for passcode entry. The [Couple Device] button is not row-level because the passcode identifies the session; the operator enters the passcode first and the matching session is resolved server-side. The coupling modal MUST display: a 6-character passcode input field (case-insensitive), an inline error area for invalid, expired, or already-consumed passcode responses, and Cancel and Couple action buttons. The modal MUST remain open on validation failure so the operator can correct the passcode without losing context. On successful coupling, the modal closes and the matched session row transitions to Assigned state in the table. Updates: FR-032 (coupling modal, inline error handling, persistent toolbar trigger, session state transition).**
- **Q: Cloud Imaging Portal OS image selection modal for single and bulk session assignment** → **A: When a session row is in the Assigned state with no image yet assigned, the row MUST display an [Assign Image] action button. Clicking it opens a modal listing the active OS image catalog as a searchable list; each entry MUST display image name, version, and file size. The technician selects one image and confirms. For bulk assignment, when one or more Assigned-state rows are checked via their row checkboxes, a context-sensitive [Assign Image to N selected sessions] toolbar button (where N is the count of checked Assigned-state rows) MUST appear. Clicking it opens the same OS image selection modal with a subtitle indicating the target session count; the confirm button label reflects N. Both single-session and bulk assignment use the same modal component. Updates: FR-033 (single-session assignment modal), FR-035 (bulk assignment reuses same modal with count-aware label and subtitle).**
- **Q: Cloud Imaging Portal session table row checkboxes, bulk selection controls, and inline expandable step detail** → **A: Each session row MUST include a checkbox for individual selection. Select All selects all rows visible under the active filter tab; Deselect All clears all selections. The [Assign Image to N selected sessions] toolbar button counts only Assigned-state rows toward N regardless of whether other-state rows are also checked. Each row MUST include a [View Details] toggle that expands an inline panel directly below the row showing: a horizontal three-node step indicator (Format, Download, Apply) visually distinguishing completed, active, and pending steps; per-step status, timestamp, and sub-progress where available; and, for Failed sessions, the support reference code and error detail inline. Multiple rows may be expanded simultaneously. Updates: FR-034 (inline expandable step progress panel per row), FR-035 (checkbox selection model and Select All / Deselect All controls).**

### Edge Cases

- What happens when a Cloud Imaging Client loses network connectivity mid-download? (Expected: resume or retry with a refreshed SAS token URL if the current SAS token URL has expired, or use cached image if available and hash matches)
- What happens when a SAS token URL expires before the download completes? (Expected: client requests a refreshed SAS token URL via the Device Gateway API, or uses cached image if available)
- What happens when a cached OS image's hash does not match the API-provided hash? (Expected: cached image is deleted, client downloads fresh copy from API)
- What happens when the USB cache partition is full and a new image is being cached? (Expected: Cloud Imaging Client skips cache storage for that session and proceeds with a direct download without error; no LRU eviction of existing valid cache entries is performed)
- What happens when two technicians attempt to couple the same passcode simultaneously? (Expected: first claim succeeds, second receives a conflict error)
- What happens when the Imaging Core API is unreachable from the Device Gateway API? (Expected: Device Gateway API returns a service unavailable response; client displays a retry-able error)
- What happens when the Imaging Core API is unreachable from the Operator API? (Expected: Operator API returns a service unavailable response; Cloud Imaging Portal and Cloud Imaging Media Builder show retry-able errors)
- What happens when an OS image upload is interrupted? (Expected: the portal detects an incomplete upload and does not add the image to the catalog)
- What happens when the USB media preparation app is asked to use a disk that contains the current Windows system volume? (Expected: operation is blocked with a hard safety error)
- What happens when partitioning fails after the cache partition is created but before boot files are applied? (Expected: app reports failure, emits support reference code, and offers cleanup/retry guidance)
- What happens when WinPE boot files are copied but auto-start registration for the client app fails? (Expected: app marks media invalid for release and provides remediation steps)
- What happens when Microsoft Graph is unreachable during the device pre-flight authorization check? (Expected: Imaging Core API returns a retriable service error to the Device Gateway API; the Cloud Imaging Client displays a retry-able error with guidance; the session remains in SessionInit state allowing the technician to retry for up to 30 minutes before the inactivity expiry elapses.)

## Requirements *(mandatory)*

### Functional Requirements

#### Cloud Imaging Client

- **FR-001**: The Cloud Imaging Client MUST present an operation selection screen as the first interactive screen after launch, titled "Cloud Imaging". The screen MUST display two operation cards: (1) "Imaging" - active and selectable, and (2) "Decommissioning" - visually disabled and marked as a future capability, not accessible in v1. The technician MUST explicitly select the Imaging card and confirm with a Continue action before any session registration or Device Gateway API call is initiated. The app MUST NOT perform any network operation or session registration until the technician confirms the Imaging operation.
- **FR-001a**: After the technician confirms the Imaging operation selection, the Cloud Imaging Client MUST register a new device session with the Device Gateway API, submitting the device serial number (sourced from Win32_BIOS.SerialNumber) and manufacturer/model (sourced from Win32_ComputerSystem.Manufacturer and Win32_ComputerSystem.Model) as part of the registration payload, and receive both: (1) a unique 6-character alphanumeric one-time pairing passcode (uppercase letters and digits only, excluding I, O, 1, 0), and (2) a high-entropy, opaque device-session token bound to that session for subsequent authenticated polling and status operations. The registration payload MUST also include detailed hardware metadata collected silently from the device before registration: motherboard manufacturer and model, BIOS version, NIC identifiers, and storage layout. This metadata is submitted for backend audit/logging and device authorization purposes and MUST be collected with no visible indication to the technician. Once session registration is initiated, the Cloud Imaging Client MUST NOT provide a back or cancel action on SessionInitView; the technician must reboot the device to return to the operation selection screen.
- **FR-002**: The Cloud Imaging Client MUST display the session passcode prominently in a clear, large font so the technician can read it easily from the WinPE device screen and enter it into the Cloud Imaging Portal without error.
- **FR-002a**: The Cloud Imaging Client MUST read the branding logo asset from the same directory as its own executable (embedded within the boot image WIM by the Cloud Imaging Media Builder Generate Boot Image workflow) and display it in the application header, aligned left, followed by the "Cloud Imaging" application name. If no logo asset is found in the executable directory, the Client MUST fall back to displaying the MSEndpointMgr default logo.
- **FR-002b**: The Cloud Imaging Client WPF window MUST target a minimum display resolution of 800x600 pixels. The window MUST be centered both vertically and horizontally on the display at all times. All UI elements across all screens (operation selection, session waiting/passcode display, imaging progress, terminal result) MUST fit within the visible window area at 800x600 without requiring vertical or horizontal scrolling. A fixed-layout design MUST be used to guarantee this across all supported screens.
- **FR-003**: The Cloud Imaging Client MUST poll the Device Gateway API every 30 seconds for state changes using the device-session token (not the pairing passcode or an Entra ID token) without freezing or degrading the UI and, when the state is SessionAssigned, MUST automatically request imaging details and continue the workflow without additional local technician action.
- **FR-003a**: When the session creation response indicates SessionNotAuthorized (device not found in any authorized source when pre-flight authorization is enabled), the Cloud Imaging Client MUST immediately transition from SessionInitView to ResultsView displaying the Not Authorized outcome. The transition MUST be immediate, with no polling delay. The Cloud Imaging Client MUST NOT proceed to ProgressView when SessionNotAuthorized is received.
- **FR-004**: The Cloud Imaging Client MUST receive a time-limited SAS token URL for Storage Account blob download access upon assignment; the SAS token URL is issued by the Imaging Core API and included in polling responses from the Device Gateway API. The SAS token URL MUST NOT be used as an API authentication credential.
- **FR-005**: The Cloud Imaging Client MUST download the OS image entirely off the UI thread and display real-time download progress.
- **FR-006**: The Cloud Imaging Client MUST apply the downloaded OS image to the target disk using DISM (or equivalent Windows imaging tool). The target disk is the disk identified and formatted during the format-disk step. **Before invoking DISM, the Cloud Imaging Client MUST compute the SHA256 hash of the locally stored OS image and verify it against the `assignedImage.sha256Hash` value provided in the Device Gateway API polling response. If the computed hash does not match the expected hash, the session MUST transition to SessionFailed, a support reference code MUST be generated using the `APL` stage code (indicating a pre-apply integrity failure), and the technician MUST be shown a clear tamper or corruption error with remediation guidance; DISM MUST NOT be invoked on a hash mismatch.** On apply failure after hash verification passes, the Cloud Imaging Client MUST transition the session to SessionFailed, report the error detail and a support reference code (format: {ComponentCode}-{SessionRef}-{StageCode}-{EpochSeconds}; e.g., CIC-A1B2C3D4-APL-1750000000) via FR-007, and display a clear failure message with remediation guidance to the technician.
- **FR-007**: The Cloud Imaging Client MUST report each imaging step's status back to the Device Gateway API in real time, and MUST provide an overall imaging progress value so the Portal can display both step-level status and a session-level completion percentage.
- **FR-007a**: The Cloud Imaging Client imaging ProgressView (screen 3 of 4) MUST display a horizontal step indicator with three labeled nodes: "Format" (format-disk), "Download" (download-image), and "Apply" (apply-image). The step indicator MUST visually distinguish completed, active, and pending steps. After the Apply step completes, the client MUST transition to ResultsView. The overall imaging completion percentage displayed in the UI MUST be based on these three steps only: (completed steps / 3) x 100, truncated to integer.
- **FR-007b**: The Cloud Imaging Client ResultsView (screen 4 of 4) MUST display one of three terminal outcomes: (1) Success - when the session reaches SessionCompleted, display a success confirmation to the technician; (2) Failure - when the session reaches SessionFailed, display the support reference code, error detail, and remediation guidance with a retry option; the Retry action MUST navigate the app back to OperationSelectionView (view 1 of 4) without requiring a hardware reboot, allowing the technician to re-initiate a fresh session with a new passcode; (3) Not Authorized - when the session reaches SessionNotAuthorized, display the device serial number and enrollment guidance instructing the operator to enroll the device in Autopilot or add it as an Intune Corporate Identifier before retrying imaging; an Exit/Close action MUST be the only available action on this outcome (no Retry button is displayed).
- **FR-008**: The Cloud Imaging Client MUST request a refreshed SAS token URL from the Device Gateway API if the current SAS token URL's expiry time is less than 15 minutes away and the download is still in progress; the Device Gateway API will source the refreshed SAS token URL from the Imaging Core API.
- **FR-009**: The Cloud Imaging Client MUST display a clear error message with a support reference code and a retry option on any failure, without any UI freeze. Support reference codes MUST use the structured format {ComponentCode}-{SessionRef}-{StageCode}-{EpochSeconds} (see Session June 22, 2026 clarification for the full format specification and stage code table).
- **FR-009a**: The Cloud Imaging Client MUST compute and store the SHA256 hash of each downloaded OS image and persist it alongside the image on the USB cache partition with metadata (image ID, version, hash, timestamp, size).
- **FR-009b**: The Cloud Imaging Client MUST, before downloading an assigned OS image, check the USB cache partition for a cached image matching the assignment's image ID and version. If a matching cached image exists, the client MUST validate the cached image's SHA256 hash against the value returned by the Device Gateway API. If the hashes match, the client MUST skip the download step and proceed with the remaining imaging workflow steps (format, apply, etc.) using the cached image.
- **FR-009c**: The Cloud Imaging Client MUST implement cache invalidation: if the cached image's hash does not match the API-provided hash, or if the cached image is corrupted/unreadable, the client MUST delete the invalid cache entry, request a fresh download from the Device Gateway API, and retry with the newly downloaded image.
- **FR-009d**: The Cloud Imaging Client MUST implement cache cleanup: cache entries not reused (no cache hit) within the last 30 days MUST be automatically removed on next boot; a cache hit resets an entry's 30-day clock, so an actively-reused image is never removed for age alone. If insufficient space is available on the USB cache partition to store a new OS image after cleanup, the Client MUST skip cache storage for that session and proceed with a direct download without error; no LRU eviction of existing valid cache entries is performed. Catalog-ID-based orphan detection (removing entries for image IDs no longer in the active catalog) is deferred to v2, as it requires a Device Gateway API catalog-query endpoint not in scope for v1.

#### Device Gateway API

- **FR-010**: The Device Gateway API MUST accept session registration requests from Cloud Imaging Client instances, including the submitted device serial number, manufacturer, and model, and MUST forward these device identity fields to the Imaging Core API as part of the session creation call. The Device Gateway API MUST return the server-generated one-time pairing passcode and the device-session token issued by the Imaging Core API (see FR-021 for passcode format, uniqueness scoping, TTL, and collision retry policy). The passcode MUST be stored only as a hash at rest and the device-session token MUST be associated with the specific session record.
- **FR-011**: The Device Gateway API MUST be publicly reachable and MUST require a valid boot media client certificate on ALL inbound requests (FR-069). The TLS handshake MUST be dropped at the platform level for any client that cannot present a certificate matching the currently active boot media client certificate; no HTTP response is returned to clients whose TLS handshake fails. This requirement applies to all Device Gateway API endpoints including the session bootstrap endpoint; no endpoint accepts requests without a valid client cert.
- **FR-012**: The Device Gateway API MUST operate with the minimum set of Azure permissions required - it MUST NOT have direct read or write access to the Storage Account.
- **FR-013**: The Device Gateway API MUST forward authenticated session and progress requests to the Imaging Core API over a Private Link connection.
- **FR-014**: The Device Gateway API MUST return OS image SAS token URLs to the Cloud Imaging Client, sourced from the Imaging Core API, on polling responses authenticated by device-session token; the pairing passcode MUST NOT be returned after SessionInit and MUST NOT be required for ongoing client polling, and the device-session token MUST be the only credential accepted for those device-originated authenticated calls.
- **FR-015**: The Device Gateway API MUST accept progress reports from the Cloud Imaging Client and relay them to the Imaging Core API for persistence.
- **FR-016**: The Device Gateway API MUST issue refreshed SAS token URLs to the Cloud Imaging Client when requested (e.g., when remaining SAS token URL lifetime < 15 minutes), provided the session is still valid and within the allowed assignment window.
- **FR-017**: The Device Gateway API MUST expose all device-facing endpoints under a URL path version prefix (`/api/v1/`) for v1. Any future breaking change to a device-facing contract MUST use a new major path prefix (for example, `/api/v2/`) rather than changing `/api/v1/` semantics in place.
- **FR-018**: The Device Gateway API MUST implement per-session rate limiting: each device session (identified by device-session token) is limited to a maximum of 10 API calls per 30-second sliding window. Requests exceeding this limit MUST return HTTP 429 Too Many Requests with a Retry-After header indicating the wait duration. Rate limiting is applied across all device-session authenticated endpoints; the session bootstrap endpoint is exempt from per-session rate limiting as no device-session token exists at that stage.
#### Imaging Core API

- **FR-020**: The Imaging Core API MUST be accessible only via Private Link; it MUST have no publicly reachable endpoint.
- **FR-021**: The Imaging Core API MUST manage the lifecycle of a device session with explicit states and transition rules: SessionInit -> [SessionNotAuthorized (terminal)] | SessionAllowed -> SessionAssigned -> SessionStarted -> SessionInProgress -> SessionCompleted/SessionFailed. When device pre-flight authorization is enabled, the Imaging Core API MUST evaluate the submitted device serial number and manufacturer/model against Microsoft Graph (Autopilot V1 and Intune Corporate Identifiers) immediately after SessionInit; sessions matching either source advance directly to SessionAllowed, while non-matching sessions immediately enter SessionNotAuthorized, a terminal state, and no manual operator approval flow is available in v1. When device pre-flight authorization is disabled, SessionInit transitions directly to SessionAllowed with no Graph lookup. Transition from SessionAssigned to SessionStarted MUST occur automatically on the client's next polling interval after assignment details are requested. Pre-imaging states (SessionInit, SessionAllowed, SessionAssigned) MUST expire after 30 minutes of inactivity. SessionStarted and SessionInProgress MUST remain active while 30-second client polling heartbeats continue, and MUST fail after more than 4 hours without heartbeat. SessionCompleted, SessionFailed, and SessionNotAuthorized MUST be auto-purged after 24 hours, requiring a new device boot/session to restart imaging. The one-time pairing passcode has its own configurable TTL (deployment parameter; default: 30 minutes) that is independent of the session inactivity timeout. The passcode is invalidated on TTL expiry or successful coupling, whichever occurs first. Passcode uniqueness is scoped to currently active (non-terminal, non-expired) sessions; passcodes from terminal or expired sessions are released and MAY be reused in new sessions.
- **FR-022**: The Imaging Core API MUST generate time-limited SAS token URLs for OS image downloads, with an expiry window configured via the PortalConfiguration sasTokenUrlExpiryMinutes setting (default: 240 minutes / 4 hours). This setting is manageable by users with the CloudImaging.Administrator role from the Portal deployment configuration section; changes take effect immediately for all newly issued SAS token URLs.
- **FR-023**: The Imaging Core API MUST expose endpoints for Device Gateway API and Operator API operations, including session coupling and image assignment.
- **FR-024**: The Imaging Core API MUST store and expose per-device imaging progress for consumption by the Operator API, including step-level state, timestamps, error detail, and an overall imaging completion percentage for each active session.
- **FR-025**: The Imaging Core API MUST have the permissions necessary to read OS images and boot images from the Storage Account and generate SAS token URLs.
- **FR-026**: When device pre-flight authorization is enabled, the Imaging Core API MUST query Microsoft Graph in parallel against two endpoints to determine device authorization: (1) GET /deviceManagement/windowsAutopilotDeviceIdentities filtered by serialNumber (Graph v1.0) to check Autopilot V1 pre-enrolled devices, and (2) GET /deviceManagement/importedDeviceIdentities filtered by importedDeviceIdentifier matching the manufacturer,model,serialNumber tuple (Graph beta) to check Intune Corporate Identifier pre-loaded devices. A match in either endpoint MUST advance the session to SessionAllowed. No match MUST immediately place the session in SessionNotAuthorized, a terminal state; the session creation response MUST communicate this status to the Device Gateway API so the Cloud Imaging Client can transition to ResultsView without further polling. The Imaging Core API managed identity MUST be granted the DeviceManagementServiceConfig.Read.All application permission in the customer tenant for these queries to succeed.

#### Cloud Imaging Portal

- **FR-030**: The Cloud Imaging Portal MUST require Entra ID authentication before any operation is accessible, and unauthenticated requests MUST be denied.
- **FR-031**: The Cloud Imaging Portal MUST display all active and recent device sessions with their current state, imaging progress, and overall completion percentage. The sessions table MUST auto-refresh every 5 seconds when one or more sessions are in an active imaging state (SessionStarted or SessionInProgress) and every 30 seconds at all other times. A manual Refresh button MUST always be visible so operators can force an immediate update. The Portal MUST NOT use WebSocket or Server-Sent Events; scheduled polling is the required refresh mechanism.
- **FR-032**: The Cloud Imaging Portal MUST allow a technician to enter a device passcode (case-insensitive input) to couple an uncoupled session; the passcode is a pairing code only and MUST NOT be treated as an API authentication credential. Invalid, expired, or already-consumed passcodes MUST be rejected with clear error messages.
- **FR-033**: The Cloud Imaging Portal MUST allow assignment of an OS image to a coupled session to initiate imaging.
- **FR-034**: The Cloud Imaging Portal MUST display per-step imaging progress for each device in real time, including the current step name, per-step status, and session-level completion percentage.
- **FR-035**: The Cloud Imaging Portal MUST support bulk operations: selecting multiple sessions and assigning an OS image to all simultaneously.
- **FR-036**: The Cloud Imaging Portal MUST allow upload of new OS images to the Storage Account with metadata (name, version, description), supporting image files of up to 20 GB. OS image upload MUST use a staged direct-to-blob upload flow: the Portal backend requests an upload SAS token URL from the Operator API (which brokers the request to the Imaging Core API), and the browser uploads the image file directly to the Storage Account blob using that URL. The image MUST NOT appear in the active catalog until the upload is fully committed and the SHA256 hash is verified.
- **FR-037**: The Cloud Imaging Portal MUST support full CRUD operations on OS images: list, view, edit metadata, delete (with guard against deleting active images).
- **FR-038**: The Cloud Imaging Portal MUST support configurable branding: custom logo, primary color, accent color, and application display name.
- **FR-039**: Branding changes MUST take effect without redeployment or application restart.
- **FR-026a**: The Cloud Imaging Portal MUST expose a device pre-flight authorization configuration setting, accessible to administrators, that enables or disables the device authorization pre-flight check globally for the deployment. This setting MUST be persisted as a portal configuration value (in a PortalConfiguration record) and MUST take effect for all new sessions immediately on save, without requiring redeployment. When the setting is disabled, all sessions advance from SessionInit to SessionAllowed without performing any Graph lookup. The Portal MUST display the current state of this setting prominently in the deployment configuration section.
- **FR-040**: The Cloud Imaging Portal MUST be built using a modern component framework and adhere to WCAG 2.1 AA accessibility standards. Its backend MUST call the Operator API for all session, image, boot image, branding, and portal configuration operations using Entra ID-authenticated access; browser code MUST NOT call the Imaging Core API directly. The Portal MUST include a deployment configuration section accessible to administrators that exposes the device pre-flight authorization on/off toggle (FR-026a) alongside other deployment-wide settings. The Portal backend MUST enforce role-based access for all API requests using the `CloudImaging.Administrator` and `CloudImaging.Technician` app roles from the shared enterprise app registration (FR-040b), restricting Operator API calls to the operations permitted for the authenticated user's role (FR-040a).
- **FR-040a**: The Cloud Imaging Portal MUST enforce the following user role access model, validated at the Portal backend on every request: users with the `CloudImaging.Administrator` role have unrestricted access to all Portal operations; users with the `CloudImaging.Technician` role have access limited to the following operations only: view all device sessions, couple sessions by passcode, assign OS images from the existing active catalog to coupled sessions, initiate bulk assignment, and monitor per-session and per-step imaging progress and the OS image catalog in read-only mode. The following operations are restricted to `CloudImaging.Administrator` only: OS image upload, edit, and delete; boot image lifecycle management (upload, publish, update, delete); branding configuration; deployment configuration including the device pre-flight authorization toggle (FR-026a); and boot media certificate management including certificate generation and rotation (FR-068).
- **FR-040b**: Both the Cloud Imaging Portal and the Cloud Imaging Media Builder MUST authenticate users against a single shared Entra ID enterprise app registration. This registration MUST define exactly two user-facing app roles: `CloudImaging.Administrator` and `CloudImaging.Technician`. The Portal SPA, Portal backend, and Media Builder MUST each validate the user's `roles` JWT claim to enforce feature access as defined in FR-040a and FR-050b. - **FR-051**: The Generate Boot Image workflow MUST bundle WinPE environment, configurations, addons, and the Cloud Imaging Client app into a relocatable boot image artifact with an embedded manifest (`ci-manifest.json`) recording image version, timestamp, component checksums (Cloud Imaging Client executable, branding logo, boot media certificate, when present), and deployment metadata. The manifest is a plain integrity/provenance record, not a cryptographically signed artifact: no genuine threat model requires signing OS boot images or the Media Builder's own downloads of them, and the independent SHA256 hash verification already required at download/deploy time (FR-056) is the real integrity boundary. The workflow MUST also retrieve the current branding logo asset from the Operator API and embed it alongside the Cloud Imaging Client executable within the boot image WIM so the Client can load it from its own executable directory at startup; if no branding logo is configured in the Portal at boot image generation time, the MSEndpointMgr default logo MUST be embedded as a fallback. The workflow MUST additionally retrieve the current active boot media client certificate PFX from the Operator API (FR-070) and embed it in the boot image WIM; if no active boot media certificate is configured in the Portal, the Generate Boot Image workflow MUST fail with a clear error instructing the technician to generate a boot media certificate in the Portal Configuration section before generating a boot image. Upload and catalog publication are handled separately by the portal upload workflow defined in FR-051b.
- **FR-051a**: The Cloud Imaging Media Builder GenerateBootImageView MUST offer two mutually exclusive source options for the Cloud Imaging Client binaries: (1) Automatic download - resolves the latest release from the MSEndpointMgr GitHub public releases API and downloads the Client binaries directly with real-time progress display (internet access required); if the API call or download fails, the app MUST retry up to 3 times with exponential backoff and, after all attempts are exhausted, MUST display a clear error message indicating the download could not be completed without automatically switching source option or prompting the technician to do so; (2) Custom local path - the technician specifies a local filesystem path to pre-downloaded Client binaries, supporting offline and airgap deployments. The view MUST also allow the technician to specify an output folder path for the generated boot image WIM artifact before generation begins. Generation MUST NOT start until a valid source and output folder are confirmed.
- **FR-051b**: Upon successful boot image generation, the Cloud Imaging Media Builder GenerateBootImageView MUST display a completion notification showing the full output folder path of the generated boot image WIM artifact and provide clear next-step instructions directing the technician to upload the WIM file via the Cloud Imaging Portal boot image catalog. The Cloud Imaging Media Builder MUST NOT perform the portal upload; upload is a manual step completed by the technician through the Cloud Imaging Portal web UI.
- **FR-051c**: The Cloud Imaging Media Builder GenerateBootImageView MUST offer an OPTIONAL driver injection step so that boot images can support target hardware whose storage controllers (e.g. Intel VMD/RST, vendor NVMe/RAID) or network adapters lack in-box WinPE drivers. The technician MAY browse to a single pre-staged "driver root" folder on the local filesystem that they populated outside the Media Builder app (the app does NOT download or manage drivers). When a driver root folder is specified, the workflow MUST recursively enumerate every driver package (`.inf`) beneath that folder and inject them into the mounted boot image WIM using DISM offline driver servicing (equivalent to `DISM /Image /Add-Driver /Driver:<driver-root> /Recurse`), forcing unsigned driver acceptance so that valid vendor packages are not rejected on amd64 WinPE. The driver root folder is OPTIONAL: when it is left empty the workflow MUST proceed without a driver injection step. When a driver root folder is specified but does not exist, generation MUST NOT start (the same validation gate as source and output folder in FR-051a). When the folder exists but contains no `.inf` packages, the workflow MUST log a warning, skip driver injection, and continue rather than fail. Driver injection progress MUST be surfaced through the same operator-visible progress and failure diagnostics required by FR-058, including the count of driver packages injected.
- **FR-052**: The Cloud Imaging Media Builder application MUST require Entra ID sign-in at application launch; SignInView MUST be the first interactive screen before OperationSelectionView or any workflow. Both the Generate Boot Image and Prepare USB Storage Device workflows require Entra ID authentication to access the Operator API. The app MUST NOT allow navigation to OperationSelectionView until sign-in completes successfully. The Media Builder MUST authenticate users against the same shared Entra ID enterprise app registration as the Cloud Imaging Portal (FR-040b); after successful sign-in, the user's assigned app role determines which workflow cards are displayed in OperationSelectionView (FR-050b). If authentication fails for any reason (incorrect credentials, MFA failure, network timeout, or token error), the app MUST display an inline error message on SignInView describing the failure and provide a Retry sign-in button; the app MUST NOT navigate away from SignInView on auth failure.
- **FR-053**: The Prepare USB Storage Device workflow MUST query the Operator API to retrieve all active boot images and present them as a selectable list in the PrepareStorageDeviceView. The latest published entry MUST be pre-selected as the default. The technician MAY select a different active entry from the list when they need to use a previously known-good boot image for a specific hardware model or to recover from a problematic latest image. The workflow downloads the selected boot image via a time-limited SAS token URL and MUST verify the SHA256 hash of the downloaded boot image file against the `sha256Hash` value returned alongside the SAS URL before deploying it to the USB bootable partition. If the hash does not match, the download MUST be retried up to 3 times with exponential backoff before aborting with a support reference code and clear error message. The branding logo is embedded within the boot image WIM artifact during the Generate Boot Image workflow (FR-051) and requires no separate retrieval or write step during USB preparation.
- **FR-054**: The Cloud Imaging Media Builder PrepareStorageDeviceView MUST list only disk devices that meet both of the following criteria: (1) bus type = USB, and (2) removable flag = true. Devices not meeting these criteria MUST be excluded from the selectable device list entirely. The host OS/system disk MUST always be blocked regardless of bus type or removable flag. Before any destructive partitioning action, the application MUST re-validate that the selected device still qualifies as a USB removable disk and is not the host OS/system disk. The device list MUST auto-refresh in response to device plug and unplug events using Windows DeviceWatcher (or equivalent WMI DeviceChanged notification); newly connected qualifying devices MUST appear automatically and disconnected devices MUST be removed. A manual Refresh button MUST also be present as a fallback.
- **FR-055**: The Cloud Imaging Media Builder application MUST create exactly two partitions on the selected USB media: one cache partition and one bootable partition for the downloaded boot image. The bootable partition MUST have a minimum size of 2 GB. The cache partition minimum size is 24 GB, which holds one OS image at the 20 GB supported maximum plus filesystem overhead.
- **FR-056**: The Cloud Imaging Media Builder application MUST download and deploy the boot image to the bootable partition entirely off the UI thread, with real-time progress displayed and ability to resume interrupted downloads. After the download completes and before deploying to the bootable partition, the application MUST compute the SHA256 hash of the downloaded boot image file and verify it against the `sha256Hash` value returned by the Operator API alongside the SAS token URL. If the hashes do not match, the download is treated as corrupt; the application MUST retry the full download up to 3 times with exponential backoff and, if all attempts fail hash verification, MUST abort the preparation workflow with a support reference code (BID stage code) and a clear tamper or corruption error. The application MUST NOT deploy a boot image to the USB partition until hash verification succeeds.
- **FR-057**: The Cloud Imaging Media Builder application MUST configure WinPE startup so the Cloud Imaging Client application launches automatically on boot.
- **FR-058**: The Cloud Imaging Media Builder application MUST provide operator-visible progress, validation output, and clear failure diagnostics with support reference codes for all stages: boot image generation, disk validation, partitioning, download, deployment, and boot configuration. Support reference codes MUST use the structured format {ComponentCode}-{SessionRef}-{StageCode}-{EpochSeconds} (CMB component code; see Session June 22, 2026 clarification for the full format specification).
- **FR-059**: The Cloud Imaging Media Builder application MUST persist a preparation manifest (`cloudimaging-manifest.json`, at the root of the bootable partition) on the USB media that records preparation timestamp, app version, boot image version, partition layout, and validation status. This manifest is the version record the Cloud Imaging Client reads at every boot to detect whether a newer boot image has since been published (FR-059a).
- **FR-059a**: The Cloud Imaging Client MUST, on every boot, perform a background, non-blocking check against the Device Gateway API for the latest published boot image version and compare it to the `bootImageVersion` recorded in the local `cloudimaging-manifest.json` on the BOOT partition it started from. If a newer version is available, the Client MUST download it, verify its SHA256 hash, and, only after verification succeeds, overwrite `\sources\boot.wim` on that same BOOT partition in place, then update the local manifest's recorded boot image version. This is safe because WinPE loads the entire boot.wim into RAM (RAMDISK boot) before the Client starts, so the on-disk file is unlocked and overwriting it has no effect on the current session; the replacement only takes effect on the device's next boot from that media. The check and any update MUST run silently: it MUST NOT block, delay, or interrupt Client startup or the current imaging session, and any failure (no BOOT volume found, no manifest, network/service error, hash mismatch, disk write error) MUST be logged as a warning and otherwise ignored, always continuing with the currently running boot.wim. The check MUST be authenticated using the Client's existing mTLS boot-media certificate against a dedicated Device Gateway API endpoint; it MUST NOT require an active device session token, since it must be able to run before or independently of session bootstrap.

#### Operator API

- **FR-060**: The solution MUST include a dedicated Operator API that serves authenticated operator workloads for Cloud Imaging Portal and Cloud Imaging Media Builder.
- **FR-061**: The Operator API MUST require Entra ID authentication for all endpoints. Service-level app roles on the Operator API govern service-to-service access: `CloudImaging.PortalAccess` (assigned to the Portal backend managed identity) grants full operator access to all endpoints; `CloudImaging.MediaBuilderAccess` (assigned to the Media Builder service principal) grants read-only access to boot images and SAS token URL generation. User-level access enforcement is applied upstream: at the Portal backend (FR-040a) and at the Media Builder UI (FR-050b), using the `CloudImaging.Administrator` and `CloudImaging.Technician` roles defined on the shared enterprise app registration (FR-040b).
- **FR-062**: The Operator API MUST provide authenticated endpoints for Cloud Imaging Media Builder apps to query available boot images, retrieve boot image SAS token URLs, retrieve a time-limited SAS token URL for the current branding logo asset in the Storage Account for embedding during boot image generation (consumed by the Generate Boot Image workflow; FR-051), and retrieve the current active boot media client certificate PFX for embedding in the boot image WIM during the Generate Boot Image workflow (consumed by FR-070); the certificate PFX endpoint MUST be restricted to the CloudImaging.MediaBuilderAccess service-level app role. The Operator API MUST additionally expose a certificate metadata endpoint (`GET /api/bootmedia/certificate/metadata`) restricted to the CloudImaging.MediaBuilderAccess service-level app role that returns the active certificate's non-sensitive attributes (thumbprint display, subject, issuedAt, expiresAt) without PFX bytes, enabling the Media Builder OperationSelectionView to verify certificate existence before the Generate Boot Image workflow begins (FR-050a).
- **FR-063**: The Operator API MUST provide authenticated endpoints for the Cloud Imaging Portal backend to manage boot image lifecycle (create upload session, upload artifact, finalize publish, list, update metadata, delete) separately from OS images, and MUST broker the staged boot image blob write and publish commit to the Imaging Core API over Private Link. The boot image catalog MUST support a maximum of 5 active entries; all active entries are eligible for selection in USB preparation sessions, with the latest published entry designated as the recommended default. **When publishing a new boot image would cause the active entry count to exceed 5, the Imaging Core API MUST automatically demote the oldest active entry to inactive status before completing the publish operation; demoted entries are retained for audit purposes and visible to administrators in a historical view, but they are excluded from active catalog queries and cannot be selected for USB preparation.**
- **FR-064**: The Operator API MUST broker operator-facing requests to the Imaging Core API over Private Link and MUST NOT directly expose Imaging Core API endpoints.

#### Cross-Cutting: Observability

- **FR-065**: All Azure Function Apps (Device Gateway API, Operator API, Imaging Core API) and the Cloud Imaging Portal backend (App Service) MUST be instrumented with the Azure Application Insights SDK and MUST emit structured telemetry including HTTP requests, outbound dependencies, exceptions, and custom trace events to a single shared Application Insights workspace provisioned as part of the deployment package.
- **FR-066**: The Cloud Imaging Client and Cloud Imaging Media Builder WPF applications MUST write structured diagnostic logs to a local rolling log file (maximum 10 MB per file, 5 files retained). They MUST NOT require network connectivity to any external APM or logging service during operation.
- **FR-067**: The Application Insights connection string for all server components MUST be injected via deployment parameters or environment variables. Hardcoded instrumentation keys or connection strings in source code are forbidden.

#### Boot Media Client Certificate and mTLS

- **FR-068**: The Cloud Imaging Portal MUST provide a boot media client certificate management capability, accessible to the `CloudImaging.Administrator` role only, within the deployment Configuration section. Administrators MUST be able to generate a new active client certificate specifying a validity period (default: 1 year; configurable at creation or rotation time). The Portal backend MUST store the generated certificate PFX in Azure Key Vault and the certificate thumbprint, subject, validity period, issued-at timestamp, expires-at timestamp, and issued-by identity in Table Storage (BootMediaCertificate entity). The Portal MUST support on-demand certificate rotation: the rotation operation MUST be an immediate atomic swap -- the new certificate is generated and activated in a single operation, instantly invalidating the prior certificate; the Portal MUST display a confirmation warning stating that all boot media using the current certificate will stop working immediately before the rotation is confirmed. No staged rotation or grace-period overlap is supported; rotation is deliberate and immediate.
- **FR-069**: The Device Gateway API MUST enforce mutual TLS (mTLS) on all inbound connections using Azure App Service `clientCertificateMode=require` on the Premium EP1 Function App plan. The TLS handshake MUST be dropped at the platform level for any client that cannot present a certificate; no HTTP response is returned to clients whose TLS handshake fails. As defence-in-depth, the Function code MUST also extract the forwarded client certificate from the `X-ARR-ClientCert` request header and validate its thumbprint against the active boot media certificate thumbprint retrieved from Table Storage; requests where the thumbprint does not match the active certificate MUST be rejected with HTTP 401. The active thumbprint MUST be cached in Function memory and refreshed from Table Storage at an interval of no more than 60 seconds to avoid per-request lookups while ensuring revocation takes effect promptly. mTLS enforcement applies to EVERY endpoint including the session bootstrap endpoint (CreateSession); there are no mTLS exemptions. Additionally, because the boot media public certificate is embedded in widely-distributed boot media and is therefore not secret, the session bootstrap endpoint MUST require an application-layer proof-of-possession: the Cloud Imaging Client signs a fresh challenge (device serial number, UTC timestamp, and a random nonce) with the boot media certificate private key, and the Device Gateway API MUST verify the signature using the public key extracted from the presented certificate and reject the request with HTTP 401 if the signature is missing, malformed, invalid, or if the timestamp falls outside the configured clock-skew tolerance. The Device Gateway API MUST additionally record each accepted nonce as single-use (an atomic insert into a dedicated Table Storage table; a duplicate MUST be rejected with HTTP 401) so that a captured signed request cannot be replayed within the clock-skew window; if the single-use check cannot be evaluated (store unavailable) the request MUST fail closed. This ensures that possession of the (non-secret) public certificate alone is insufficient to create a session even if the forwarded-header trust boundary is ever weakened.
- **FR-070**: The Cloud Imaging Media Builder Generate Boot Image workflow MUST retrieve the current active boot media client certificate PFX (certificate and private key) from the Operator API alongside the branding logo before assembling the boot image WIM. The PFX MUST be embedded in the boot image WIM at the fixed relative path `certificates\bootmedia.pfx` inside the Cloud Imaging Client executable directory (i.e., at `<wim_client_exe_dir>\certificates\bootmedia.pfx`). This path is a fixed contract between the Media Builder and the Cloud Imaging Client; neither component may deviate from it. If no active boot media certificate is configured in the Portal at boot image generation time, the Generate Boot Image workflow MUST fail with a clear error message instructing the technician to generate a boot media certificate in the Portal Configuration section before generating a boot image; generation MUST NOT proceed without a valid active certificate.
- **FR-071**: The Cloud Imaging Client MUST load the boot media client certificate PFX from the fixed path `certificates\bootmedia.pfx` relative to its own executable directory at application startup and configure it on all HTTPS connections to the Device Gateway API via `HttpClientHandler.ClientCertificates`. This path is a fixed contract with the Media Builder (FR-070); the Client MUST NOT search any other path. If the PFX file is not found at that path, or if the TLS handshake with the Device Gateway API fails due to certificate rejection (SSL/TLS error or HTTP 401 cert-mismatch response), the Cloud Imaging Client MUST transition to a dedicated error state on SessionInitView displaying a clear message that the boot media certificate is missing or no longer valid and instructing the technician to regenerate the boot image using the Cloud Imaging Media Builder and re-prepare USB media with the new image. No automatic retry is offered for a certificate rejection error; the technician must replace the USB media.

### Key Entities

- **DeviceSession**: Represents a single imaging session for one device. Attributes: session ID, pairing passcode hash (derived from 6-character code format uppercase A-Z and 0-9 excluding I/O/1/0), one-time passcode expiry/consumed flags, opaque device-session token reference, token expiry, state (SessionInit -> [SessionNotAuthorized (terminal)] | SessionAllowed -> SessionAssigned -> SessionStarted -> SessionInProgress -> SessionCompleted/SessionFailed), device serial number, device manufacturer, device model (captured at session registration from Win32_BIOS/Win32_ComputerSystem), device hardware metadata (motherboard manufacturer and model, BIOS version, NIC identifiers, storage layout; collected silently at session initialization and stored for audit), pre-flight authorization result (matched-autopilot-v1 | matched-corporate-identifier | not-authorized | skipped), assigned OS image reference, current SAS token URL and expiry, last heartbeat timestamp, per-step progress details keyed by step identifier (format-disk, download-image, apply-image), overall imaging completion percentage, created timestamp, terminal timestamp, and purge-at timestamp (24-hour terminal retention).
- **OSImage**: A Windows OS image stored in the Storage Account. Attributes: image ID, name, version, description, size, storage path, upload date, in-use flag, SHA256 hash (for cache validation).
- **CachedOSImage**: A cached OS image on the USB cache partition. Attributes: cache ID, source image ID, version, SHA256 hash, cached timestamp, size, last-accessed timestamp.
- **ImagingStep**: An individual step within an imaging job. Attributes: step name, status, started-at, completed-at, error detail, and stepProgressPercent (optional, integer 0-100) when a step can report sub-progress.
- **SASTokenUrl**: A pre-signed, time-limited URL for OS image blob access that embeds the SAS token credential for direct client download from Storage. Attributes: URL, expiry time, associated session.
- **BrandingConfiguration**: Portal branding settings. Attributes: boot-media logo blob path and portal header/sidebar logo blob path in Storage Account (each logo is stored as a blob; the boot-media logo is accessed via SAS token URL, the portal logo is streamed directly), primary color, accent color, application name, and independent light/dark background colors for the sidebar, header, card, and page surfaces.
- **PortalConfiguration**: Deployment-wide portal configuration settings persisted in Table Storage. Attributes: devicePreFlightAuthorizationEnabled (boolean, default true), sasTokenUrlExpiryMinutes (integer, default 240; modifiable by CloudImaging.Administrator role from Portal deployment configuration section; takes effect immediately for all newly issued SAS token URLs), last-modified timestamp.
- **BootMediaCertificate**: The active client certificate used by Cloud Imaging Client instances to authenticate the boot media origin via mTLS to the Device Gateway API. Managed exclusively by CloudImaging.Administrator role in the Portal Configuration section. Attributes: certificate ID, thumbprint (SHA-256), subject, validity period (configurable, default 1 year), issued-at timestamp, expires-at timestamp, issued-by (Portal user identity), status (active); PFX (certificate and private key) stored in Azure Key Vault; only one certificate is active at any time; rotation replaces the active certificate immediately with no overlap period.
- **BootImage**: A prepared WinPE + Cloud Imaging Client application package suitable for deployment to USB media. Attributes: image ID, version, created-at timestamp, boot image size, manifest content, storage path in blob.
- **BootImageManifest**: Metadata embedded in a boot image. Attributes: manifest version, image version, created timestamp, WinPE version, client app version, component checksums, deployment instructions.
- **UsbPreparationProfile**: Input configuration used by the Cloud Imaging Media Builder app. Attributes: profile ID, WinPE source path, client payload path, cache partition size, boot partition label, cache partition label.
- **UsbPreparationManifest**: Output manifest generated after USB media preparation. Attributes: manifest version, preparation timestamp, tool version, boot image version, selected disk identifier, partition schema, validation results, auto-start configuration status.

## Assumptions

- Devices are running a WinPE environment with outbound network connectivity (wired or Wi-Fi) to reach the Device Gateway API endpoint.
- Technicians run the Cloud Imaging Media Builder application on Windows 10/11 devices with administrative rights required for disk partitioning and boot file operations.
- Technicians and administrators have valid Entra ID credentials and are assigned to the `CloudImaging.Technician` or `CloudImaging.Administrator` app role respectively in the shared Entra ID enterprise app registration (FR-040b); Portal feature access and Media Builder workflow availability are governed by this role assignment.
- The organization's Entra ID tenant has been configured in the deployment for Cloud Imaging Media Builder and Cloud Imaging Portal authentication.
- Azure infrastructure (Storage Account, Device Gateway API, Operator API, Imaging Core API, App Service, Private Link, Entra ID) is pre-provisioned prior to first use.
- Cloud Imaging Portal authentication is handled via Azure Entra ID (enterprise identity); device-level pairing uses the one-time session passcode, while ongoing Cloud Imaging Client API calls use a separate device-session token.
- The Cloud Imaging Client operates in a minimal-trust, ephemeral environment: no pre-shared secrets or hardcoded service credentials are embedded in the WinPE image; the boot media client certificate PFX embedded by the Media Builder during boot image generation is the only credential present, is issued and managed through the Portal (FR-068), and authenticates the boot media origin to the Device Gateway API via mTLS (FR-069, FR-071).
- One active imaging session per device at a time; concurrent sessions on the same device are not supported in v1.
- OS images stored in the Storage Account are in a format compatible with the Windows imaging toolchain (e.g., WIM or ESD); format validation is out of scope for v1.
- Mobile-optimized Cloud Imaging Portal layout is out of scope for v1 (desktop browser is the primary target).
- SAS token URL expiry defaults to 4 hours and is configurable per deployment by an administrator.
- The Cloud Imaging Portal is a community-distributed solution; all configurable defaults MUST be documented clearly for self-hosters.
- The solution is developed and maintained by two core contributors who share a single joint Azure subscription for all development and validation; the core team deploys to that environment exclusively via GitHub Actions workflows (FR-047) for both initial infrastructure provisioning and iterative feature development. Once a new version is ready and validated in that shared environment, it is packaged and published as a GitHub Release for public self-hosters to adopt. Each GitHub Release is a complete, versioned bundle containing release artifacts from all six components (seven artifacts in total: three Function App packages, Portal frontend and backend counted separately, Cloud Imaging Client WinPE binary, and Media Builder installer), IaC templates, parameter templates, and documentation regardless of which individual components changed since the prior release; no component is published independently and versioning is solution-level; GitHub Actions deployment workflows and VS Code workspace configuration are excluded from community release bundles as they reference team-specific Azure credentials and environment secrets. Self-hosters adopt a new release by downloading the release archive and running the included upgrade script (update.ps1) against their existing Azure deployment; the upgrade script is idempotent and applies all necessary infrastructure and application changes without requiring manual resource re-creation or re-entry of unchanged parameter values.
- USB media prepared by Cloud Imaging Media Builder includes exactly two partitions: a cache partition for OS image caching (sizing per deployment, minimum 24 GB, which accommodates one OS image at the 20 GB supported maximum plus filesystem overhead) and a bootable partition for WinPE boot image deployment (minimum 2 GB; typical WinPE + Cloud Imaging Client payload is under 1 GB).
- Portal branding (logo) MUST be configured before generating a boot image using the Cloud Imaging Media Builder if custom branding is required; the branding logo is embedded within the boot image WIM artifact during the Generate Boot Image workflow. Re-generation of the boot image is required to update branding on existing USB media. If branding is not yet configured at boot image generation time, the MSEndpointMgr default logo is used.
